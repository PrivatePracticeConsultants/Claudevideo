Labels: **CONFIRMED** = reproduced live on head; **PLAUSIBLE** = read in the
code, not run (or the mechanism ran but the real-world trigger is assumed).

## 2. What is wrong, by severity

### P0 — data doubled, or a real file never loaded / silently stale

**P0-1 (CONFIRMED mechanism, PLAUSIBLE frequency) The same content under different bytes loads twice — identity is the raw sha only.**
`s3_identity.py` A1–A4, `s2_early.py` F (`s3.out`, `s2.out`): gz level 1 vs level 9 of one document → 2 files `done`, 600 rates for 300; `.json` + `.json.gz` → 600; a link's raw `.gz` + a browser-saved copy (the browser DECODES a `Content-Encoding: gzip` body before saving — the shape `_body_chunks` (`fetch.py:612`) explicitly keeps raw because "S3 objects stored with Content-Encoding: gzip metadata" exist) → 600; a host that serves the `.json.gz` inflated → 600. Medians are unchanged (identical values pool to themselves) but every raw count, `source_count`, the "Pooled months" note, the part on disk and the parse time double, and the methodology lists two files. No decompressed-content fingerprint exists anywhere (`grep` of `content_fingerprints` columns: size/head/tail/win/magic/full_sha/mtime/trailer_proves — all raw).
*Cost of one, measured (`s3b.out`, page cache warm, best of two):* sha256 of the inflated stream costs **+0.77 to +0.97 s per GB inflated** on this box (sha256 ≈ 1.3 GB/s; inflate alone ≈ 450–1,100 MB/s) — UHC-NY 36 MB gz → 623 MB: +0.60 s; River Valley 262 MB gz → 5.5 GB: +4.2 s. The parser already inflates every byte, so for the INBOX the hash can ride on `open_stream`'s reader during the identity read (which would then also have to inflate: ~2 s/GB compressed more than today's raw read) or during the parse (then the claim can only be checked after the parse — a decoded twin would be dropped, not skipped). For a LINK the download already streams the raw bytes through `ContentHasher`; inflating on the fly with `zlib.decompressobj(31)` and hashing the output puts the decoded sha next to the raw one at zero extra I/O (CPU ≈ 1 GB inflated / 2.5 s, far below network speed). Store it as a second column (`content_sha_inflated`), claim on EITHER sha in `claim_content_ingest`/`claim_inbox_content`, and the early check stays as is. Define it as sha256 of the container-stripped byte stream before BOM removal (a `.json` hashes itself).

**P0-2 (CONFIRMED) A republished file is silently left at the old month by the monthly refresh / re-expansion.** Three shapes, `s6_refresh.py` (`s6.out`):
- **A** (the round-13 diff finding, re-reproduced on head): a child loaded by 0.7.4 (no `server_validator`/`server_size`) behind a server whose 1-byte probe answers a chunked 200 with no size and no validator → `_republished` = None, but `then_size = loaded_size` is set so the row is not in `unknown` either → **nothing queued, no note; rates stay 2026-05**. Requests: `/index.json 200`, `/r.json.gz bytes=0-0 200`. `fetch.py:2930-2936` (`elif verdict is None and parent_reval == 1 and now is not None and not r["server_validator"] and not then_size`).
- **C**: new bytes AND a new size (1,505 → 2,174 B) behind an UNCHANGED ETag → `_republished` returns `tv != nv` = False and never looks at the size → **left at 2026-05, no note**. `fetch.py:2615-2627`. A stale validator is a server bug, but the size is free and already in hand.
- **B / H / I**: same size, bytes changed, no validator (B, I) or same validator (H) → "unchanged". This is the residual GETTING_STARTED admits for resumes; on the refresh path nothing on the row says the check was by size only, and the child-requeue path (I) says "the payer still publishes the same file".
Fix: compare the size whenever both sizes are known even when validators agree; when the probe yields neither and nothing but a loaded size exists, treat as `unknown` on the monthly refresh (download) or at least write "could not tell whether the payer changed this file" on the row; write "last checked <date>: unchanged by <ETag|Last-Modified|size>" on every probed child.

### P1 — the user must act and nothing tells them

**P1-1 (CONFIRMED with `LOCAL_HASH_MAX_BYTES` lowered to 1 MB; the 4 GB value not exercised on disk — 6.5 GB free)** Over 4 GB, an inbox file's identity is size + mtime only, and `_finish_ok` records `trailer_proves = None` (no hasher ran, `ingest.py:384-404`). Consequences (`s3.out` C): inbox + inbox twin under a second name → **both load (3,000 rates for 1,500)**; inbox first then the same bytes by LINK → **both load** (the link's claim finds no `full_sha`; the early check finds a candidate but `_proves` needs `trailer_proves == 1`). Link first then inbox IS caught (`_big_local_twin` proves against the link's recorded trailer). A same-name re-drop of a COPY (new mtime) is held as "A different file …" when it is the same file. The code path is exactly the one a user hits with national files (the files big enough to be dropped by hand). Fix: in `_finish_ok` for a big file, read gz members + fingerprint in one pass (`file_identity` already does that; cap only the FULL sha, not the proof), so `trailer_proves` is recorded and `_proves` can hold for both later paths; say "identical by size, beginning, end and samples (over 4 GB the full checksum is not taken)" on the skip.

**P1-2 (CONFIRMED) After the user adds billing codes, nothing re-reads the files already loaded, and the documented action does nothing.** `s9_zero.py` (`s9.out`), `s7_revive.py` C: a 0-row file is `done` and fingerprinted; after adding the code, re-pasting the child link → `{'added': 0, 'skipped': 1}`, 0 requests; re-pasting the index → probe only; the monthly refresh → probe only; the inbox re-drop → 'same'. GETTING_STARTED.md:688-690 ("re-add those links — the app re-downloads and re-extracts them") and `cli.py:717-719` ("re-add links to pick the new codes up in files you already have") are **wrong**. What works today: Files tab remove / `mrfx forget <file>` then re-paste (links), or `mrfx ingest --force` with the file in the inbox. Fix: either make a direct re-paste of a `done` rate row re-fetch (it anchors content dedup only through `content_sha`, which a reload re-records — `record_identity` already handles replaced content), or a `mrfx reextract` / "re-extract with the current code list" button that re-queues every done rate row with `revalidate=2`; and fix the two sentences.

**P1-3 (CONFIRMED) The monthly refresh covers only catalog sources, and is off by default.** `s10.out`: a user-pasted static index that is not in `known_sources.yaml` keeps its `done` row forever; nothing on the Links tab says "last checked". A re-paste of the index does work (D12) — the user has to know to do it. Fix: refresh every done top-level index the user pasted, or say on the row when it was last expanded.

**P1-4 (CONFIRMED, narrow) Files loaded before audit 8 have no identity row and the Files tab does not say so.** `s5_samename.py` D (`s5.out`): with the processed copy gone, a corrected same-size file dropped under the loaded name with an OLDER mtime (`cp -p`, a restore) is silently 'same' (`ingest.py:1887-1897`: size equal and `mtime <= finished_at`); the rates stay at the old value and the corrected file is moved to `processed/` under that name, which then poisons the next drop too. `/api/files` exposes no "identity recorded" field, so the user cannot tell which files are in that state. Fix: drop the mtime-age fallback (hold for choice instead — one click) and backfill identities for every file still in `processed/` at start.

### P2 — waste

**P2-1 (CONFIRMED mechanism)** `dedup_key` never strips Google Cloud Storage V4 (`X-Goog-Signature/Date/Credential/Expires/Algorithm/SignedHeaders`), Akamai `__token__`, or a bare `?token=<JWT>` with no `sig` (`s1.out`). A re-pasted or monthly re-expanded GCS index makes a NEW row per child per visit (`s6.out` G: 1 MB + a tail and 8 window ranges = 1.5 MB of 206s for an unchanged 3.7 MB gz child; a `.json` child downloads in full) and rows accumulate monthly; the old row is never probed. No payer in the catalog is known to use GCS signing — PLAUSIBLE, not observed. Fix: add `x-goog-(algorithm|credential|date|expires|signedheaders|signature)` to the always-stripped set and `__token__`.
**P2-2 (CONFIRMED mechanism, PLAUSIBLE shape)** `?token=<file id of ≥ 20 chars>&sig=…` collapses two files to one key (`s1.out`); the second file is reported "already known". The 2.10 fix protects short ids only. Fix: when stripping an ambiguous param would make two listed URLs equal, keep it (dedup within the listing), or require the value to look like a SAS/JWT (contains `%`, `=`, `.`, or is ≥ 40 hex chars) rather than merely ≥ 20 chars.
**P2-3 (CONFIRMED)** Re-pasting a `skipped/duplicate` link re-downloads it: with the default 15 MB check a 3.7 MB gz downloads in full and is re-skipped by sha; a bigger gz costs 15 MB + 1.5 MB; a `.json` the whole file (`s7.out` A). GETTING_STARTED:674 says a re-add "costs nothing (skipped by content)". Fix: on a direct re-paste of a `skipped/duplicate` row whose `duplicate_of`/sha twin is still `done`, answer "already loaded as X" without queueing (the user can still press retry).
**P2-4 (CONFIRMED)** A multi-member (bgzip) TRUE twin and every plain-`.json` twin download in full before the sha skip (`s2.out` C2/D2) — by design (safe direction); the early note "copies of a loaded file are recognised after the first 15 MB" on the Links tab is true only for single-member gz/zip.
**P2-5 (CONFIRMED)** Name-based exclusions in UHC/Optum listings drop in-network files whose employer name contains `allowed` as a substring or an `_NDC`/`-NDC` token (`s8.out`: "Hallowed-Health", "Allowed-Benefits-TPA", "NDC-Corp"), silently (one INFO line with counts). Fix: match `allowed-amounts`/`allowed_amounts` only, and let a dropped-by-name entry be queued when the TOC also lists it; or record the exclusions on the listing row.
**P2-6 (CONFIRMED)** A child removed from the index stays `done` with no note (`s6.out` D) — its month stays in the pooled history, which is right; but a user looking for "what the payer stopped publishing" has nothing.

### What was checked and is RIGHT (so nobody re-audits it)

Early check: true gz/zip twin skipped after 1 MB with the partner named; a same-size one-rate change in a single gz, a multi-member variant, a plain-json variant and a zip variant all LOAD (`s2.out` A/B/C/D/G/G2); a `Content-Encoding: gzip` body is kept raw and proves (E). Content claims: two hosts, four concurrent links, link+inbox both orders → exactly one load; a failed first loader (link or inbox) hands the load to the twin (`s4.out`). Same-name: same bytes skipped by sha; corrected same-size file held; `.held` survives restarts; Replace loads from `.replacing`; Keep both → `name-<sha8>.json.gz`; another month loads beside (`s5.out`). Refresh: a child republished with a new validator reloads; month-dated children of a static index: old row stays done, new month loads; a child whose URL changed but bytes did not is downloaded then skipped by sha (`s6.out` E/F, `test_review11/12`). Revive: canceled re-paste loads; oversize re-paste re-checks the size; a queued row takes the fresh signature and a downloading row keeps its own; a done row's url is kept fresh (`s7.out`). Catalog: 150 sources, no URL twice; dated template → new row per month; static → one row (`s10.out`). Sniff: content decides, not the name (`s8.out`).

## 3. The protocol in one page (for AI_HANDOFF)

1. **A LINK is one queue row per `dedup_key`** = `scheme://host(lower)/path(as is)?sorted query minus signature params` (always: `expires signature policy key-pair-id awsaccesskeyid sig x-amz-<signing>`; beside a signature param also the Azure SAS names and `token/st/policy` when the value looks signed). Not covered today: `X-Goog-*`, `__token__`, a lone JWT `token`. `http`/`https`, `:443`, trailing slash, percent-encoding and host aliases are DIFFERENT rows; content decides later. A paste of an existing key refreshes the row's url (not in flight) and revives `failed` / `skipped` (any kind) / `oversize` / a done index; a re-expansion revives only `failed` and an oversize that now fits. **A done RATE row is never re-fetched by a paste** — only forget + paste, the monthly refresh, `requeue_url_for_file`, or a re-expansion that finds it republished.
2. **Children**: `expand_toc` takes every http(s) location (no name filter, deduped by key, capped and SAID); the UHC/Optum `blobs` listing drops names containing `allowed` and `(^|[-_])ndc([-_.]|$)|prescription-drug` (log only); page links are only RANKED by name.
3. **Early skip (15 MB)**: size + head equal to a LOADED file → fetch tail + 8 windows by Range; SKIP only when gz/zip on both sides and the twin's `trailer_proves = 1`; an earlier in-flight match WAITS. Plain `.json`, multi-member gz, and anything unprovable download in full. The row says "checksum-equal to <url> … skipped after X MB", `duplicate_of` set.
4. **Identity = sha256 of the RAW bytes** (hashed while downloading; one sequential read for an inbox file ≤ 4 GB). Re-encoded content (another gzip level, `.json` vs `.json.gz`, a decoded copy) is a DIFFERENT file and loads twice — there is no decompressed-content fingerprint. Over 4 GB an inbox file has size + mtime only and no `trailer_proves`; only "link first, inbox second" is caught.
5. **One content claim for every path** (`claim_content_ingest` / `claim_inbox_content`, one lock): a loaded twin → `skipped/duplicate` with the partner named; a twin loading now → defer (link) or wait (inbox), revived on the twin's failure, at start-up, or by `record_identity` when the twin's content is replaced. Exactly-once holds under concurrency and failure.
6. **Same name in the inbox**: 'same' = recorded size+mtime, or equal full sha, or sha-equal to the processed copy; for a file with no identity row and no copy, size equal + mtime ≤ finished_at (legacy fallback; a false 'same' is possible). Different bytes, same payer+month → HELD for Replace / Keep both; another month → loaded beside as `name-<sha8>`.
7. **Re-check of a loaded link** = one 1-byte ranged GET: validator differs → re-download; validators equal → unchanged (the size is NOT consulted); no validators → size decides; neither → re-download (child, monthly refresh) only when no size was ever recorded — a loaded size with a size-less probe is "unchanged" (stale, silent). Nothing is written on an unchanged child.
8. **Monthly refresh** is opt-in and catalog-scoped: dated templates get a new row each month; static catalog indexes are re-expanded once a month; a user-pasted index is never re-checked.
9. **0-row files** are done, fingerprinted and anchor dedup like any file; a code-set change re-reads nothing — forget + re-paste, or `mrfx ingest --force`.
10. **Kind** is decided by content (first 1 MB of keys), never by the file name; the zip member read is the largest `.json`.
11. **Forget** keeps the url row as `skipped` (sha kept, twins neutralised) so a re-paste reloads; the early/sha skip text always names the partner; the silent decisions are listed in §2 P3.
